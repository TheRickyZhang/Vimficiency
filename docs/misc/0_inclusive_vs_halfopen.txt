  Summary: Inclusive vs Half-Open Boundaries

  Current State

  The codebase consistently uses inclusive [first, last] semantics for:
  - Range (character-wise): first and last Positions, both included
  - LineRange (line-wise): firstLine and lastLine, both included
  - Lines::getSpan(front, back): both endpoints included

  Where Conversions Happen

  The +1 conversions are localized to:
  1. VimEditUtils.cpp:25,50,85 - STL erase()/substr() calls
  2. Lines.h:128,134 - getSpan() extraction

  My Recommendation: Keep Inclusive

  Inclusive is the right choice for this codebase because:

  1. Vim's mental model is inclusive - Vim motions describe endpoints as "the character you land on", not "one past". When e moves to word end, that's the actual last character, not a half-open sentinel.
  2. Endpoint functions return natural positions - motionWordEndpoint() returns where the cursor lands. With half-open, you'd need +1 at every endpoint computation instead of at consumption.
  3. Text objects would be confusing - iw on "hello" (5 chars) at position 0 would return Range({0,0}, {0,5}) but position {0,5} doesn't exist. The current Range({0,0}, {0,4}) directly maps to valid cursor positions.
  4. Conversion is localized - Only ~5 places need +1, and they're at the STL boundary where the semantic shift is expected.

  Potential Minor Improvements

  If you want to reduce conversion noise without changing semantics, consider helper methods:

  // In LineRange
  int lineCount() const { return lastLine - firstLine + 1; }

  // In Range (single-line only)
  int charCount() const { return last.col - first.col + 1; }

  One Possible Exception

  LineRange is the closest candidate for half-open because line-wise deletions (dd, d3j) map directly to lines.erase(begin_iter, end_iter). But even here, Vim documentation says "delete lines 3 through 5" (inclusive), so the mental model benefit
  outweighs the STL convenience.

  Bottom line: The current inclusive convention aligns with Vim semantics and keeps the domain model clean. The conversion cost at STL boundaries is acceptable and clearly localized.
