Interesting (maybe?) things that have come up:
- C ABI
- C++ Name Mangling
- X Macros. May become obsolete with reflection in C++ 26?
- std::streambuf, and cout.rdbuf as getter/setter
- CMake visibility: public, private, interface
- When you need same type of space per many function calls, static declaration has downsides over stack: not safe to recursion, worse cache behavior. 
- Map<T> uses std::less<T> as the comparator by default, which can only take in T. But if we pass std::less<>, which is "transparent", now we can have anything comparable to T, like string vs string_view.
- Similarly, we can implement transparent std::equals<>, and hash callable, which uses pre-concept check of: "using is_transparent = {whatever}"
- Other built-in nested type checks:
  Allocator: is_always_equal, propagate_on_container_{...}
  Iterator: iterator_category
  Tag dispatch types, mutex/lock tags, memory order tags
  Execution policies
  Pointer traits

- You can't store references in initializer list, but can use a reference wrapper (basically use * as underlying, with & interface) to get around.
- Difference in the way types are returned depending on if simple and <= 16 bytes: use register vs pass hidden pointer
- Use a hash function to change long if/else chain to switch case
- You can use iterator construction for anything as long as value_type convertible to T
- You need extra {} scope in switch statement to not leak definitions (at underlying jump table, they are not separate blocks)
- Difference between default stream formatting and to_string(), such as for printing doubles.
- std::pmr (C++ 17)
- Compared to += or appending, prepending to a string (ig: str = s + t) does an allocation, so you should prefer insert instead.
- Use strcmp for comparing values of const char*, since == compares the addresses. (Prefer to use string::view, even though 8 more bytes)
- Look into std::ranges stream-like API; can be powerful, but verbose
- Violating ODR through lib like GoogleTest can result in malloc/memory failures very difficult to debug.
- Implementing concepts, first with Indexable in tests/Utils/RandomGeneration
- Funargs and scope of nested functions
- Micro-benchmarking with GoogleTest for fundamental choices/impl, but doesn't give full picture of tail latency under real load for trading systems.
- Aggregate is formally defined in the standard: Basically a minimal, public DTO (struct/class with only public data members). Can use designated initializers (C++ 20)
- Note we cannot have same named structure with functions, because while the storage is part of a struct's type interface, function parameters are positional (order only affects how they are pushed onto the stack). But a workaround is to pass struct as argument.
- Inlining, as in substituting the definition in place of where it is called (happens after IR step), improves optimization decisions with visibility so long as it does not bloat the cache too much. Driven entirely by compiler unless explicitly overridden.
- "inline" the keyword is only about linkage, ie we should deduplicate this definition in the header file.
- Usage of string::resize_and_overwrite (C++ 23) as a better alternative to reserve and push_back. No equivalent exists for vector yet.
- Usage of .template / ::template disambiguation
- Impact of stale object files (or potential compiler bug, but wasn't able to reproduce) when using inline helper functions passed as template arguments
- Elegance of QuickCheck (Haskell/OCaml) as property-based checking library with generator composition and lazy evaluation shrinking -> RapidCheck in C++ with GTest integration.
- ODR violations are very insidious, with complete undefined behavior. Very easy to make without compiler warning with naming google tests!
