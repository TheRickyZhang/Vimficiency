Lay the initial text down the side and the goal text across the top. A cell
`(i, j)` means initial `[0, i)` has been consumed and goal `[0, j)` produced.
A plan is a path from the top-left corner to the bottom-right one.

<figure class="vf-figure">
  <Lattice />
  <figcaption>The three step families as moves on the grid. A region is a run of delete and type steps between two moves.</figcaption>
</figure>

- **move** steps diagonally while the characters match, paying the counted-motion cost of the span crossed
- **delete** steps down, paying the counted-operator cost of the initial span removed
- **type** steps right one goal character at a time, paying that key's effort

The cheapest path is the cheapest plan, and reading the regions off it is a
walk back through each cell's predecessor.

## Two tables

Typing happens in insert mode and everything else in normal mode, so each cell
exists twice: `out[i][j]` for normal mode and `in[i][j]` for insert mode.

```
move    out[pi][pj] → out[i][j]   i-pi = j-pj ≥ 1, chars match          moveCost(pi, i)
        previous block's trailing diagonal → this block's leading one   moveCost(seal)
delete  out[pi][j]  → out[i][j]   delete initial [pi, i)                 delCost(pi, i)
        out[pi][j-1] → in[i][j]   same, landing in insert via `c`        delCost(pi, i) + esc + typed
type    out[i][j-1] → in[i][j]    enter insert, type goal char j-1       entry + esc + typed
        in[i][j-1]  → in[i][j]    type goal char j-1                     typed
        in[i][j]    → out[i][j]   leave insert                           0
```

- nothing is charged per region, so a state needs no memory of where its region began; that is why two tables suffice
- the two sides behave differently, which is why there are two: typing is additive per character, so `in` extends one character at a time, while a deletion is not — a span that grows to swallow a whole line becomes one `dd` — so every delete arrival is priced by a [sweep](/Vimficiency/docs/how-it-works/pricing-spans/) from its start
- each cell keeps one candidate: its cost, the step that produced it, and the predecessor cell

<GridWidget />

Hover a cell to see its cost and where it came from. The `in` table is reached
only through `ENTER` or `CHANGE` and left through the free `EXIT` edge; the
optimal path (yellow) jumps between the two tables at those points. The large
dots mark path cells in the table you are viewing, the small ones its cells in
the other table.

On `aa b cc` → `xx b zz` the winning path runs `DELETE` down the whole left
column and then `TYPE` across: one region, the `C` plan. Change the goal to
`xx b cc` and the path turns into a diagonal `MOVE` after the first edit.
